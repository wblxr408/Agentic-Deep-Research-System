## 为什么预设 JSON 仍会重复

1. `response_format={"type":"json_object"}` 约束 JSON 输出；`ModuleReportDraft` 再约束标题、模块、段落类型、长度及引用数组。两者都没有证明跨段命题不同。
2. 分章写作让同批成果分别进入全景、演进、深读、验证和行动。章节职责与前章上下文已经进入提示，但独有判断仍依赖模型理解；这些提示不是语义唯一性的确定性约束。
3. `report_editorial.select_paragraphs` 保证每个段落 ID 在主文、附录或省略中恰好出现一次。不同 ID 完全可以表达同一件事。该步骤禁止改写文字；一段同时含有独有机制和重复范围句时，搬到附录仍会保留重复。历史选择响应曾将 12 个 ID 同时列入附录和省略；结构修正后选择 31 段主文、57 段附录，没有省略段落。结构有效不能当成去重完成。
4. 旧读者审核只提供少数 `anchors` 示例和自然语言修订建议。局部编辑允许修改的 ID 来自这些示例及意见中的显式 ID，其他重复位置是只读上下文。于是一次改掉几处，下一轮重新发现其余重复，形成多轮往返。
5. 原 reading 标准没有充分区分必要的本地实验条件、摘要预告和无新用途的范围说明。过宽的修订建议可能要求删掉必要条件，或为章节差异补做新对比。最终事实审核又会阻止没有来源的新事实，造成两个要求之间的拉扯。

## 当前流程与终止条件

正常路径为：分章写作 → 整段归属选择 → 依据主文写开篇 → 报告装配 → 逐声明来源审核及有界事实修正 → 最终读者任务审核 → 必要的一次阅读编辑 → 再做事实与读者审核 → 图表和原图解说审核 → 发布和导出。

读者审核使用现有冻结的报告模型和预算，本根为 DeepSeek `deepseek-flash`；它是另一阶段的编辑判断，不是已经取得独立人类读者反馈。审核读取实际主文、附录、采纳成果、技术卡、行动和研究判断，不只检查模块非空或支持率。每个适用标准必须恰好判断一次，通过项必须有逐字报告定位，每项采纳成果必须交代去向。格式、定位或覆盖无效时是 incomplete；有效判断有任一 gap 时是 needs_revision；全部 satisfied 才能通过。

一次正常报告调用最多审核两轮，中间最多自动编辑一次。已有 `reader_revision` 或 `structural_revision_attempted` 标记时不再自动编辑。仍有缺口则暂停。同根显式 reader-revision 接续受本人、原执行、来源、模型、输入、账本和期限检查约束；基础编辑机会为一次，现有进展、格式、预算或传输恢复分支另有绑定条件。原 `reader_note_recovery` 以新的审核 binding 允许接续，不要求语义问题严格下降，因此新稿件不等于缺口已收敛。这一入口不能代替读者门，也不是无限自动重试授权。

历史记录中还发生过无效逐字锚点、归属格式错误、检查点保存超时和工作进程退出。它们分别阻塞了流程；最后保留快照的直接阻塞已经是有效的 reading 缺口。

# ADRS 核心思想

**以简洁的设计，让用户看懂研究计划，并通过可靠的工具接口完成可核查的研究。**

这是 ADRS 的长期设计与评审准则。五个技术主题、DAG、多 Agent 和框架选型都服务于研究任务的完成。以下要求约束后续设计；实际实现和验证范围以代码及专项交付记录为准。

## 1. 简洁性：采用完成任务所需的最小结构

- 优先使用普通函数、明确的数据契约、显式状态和直接工具调用。增加 Agent、路由层、包装器或服务时，应说明它解决的具体问题及维护成本。
- 只有职责、上下文或权限需要独立边界时才拆分 Agent。现有搜索、浏览、内部资料检索按需调用，避免为了展示协作而强制串联。
- 公开研究默认联网；内部资料检索是按需补充，不作为强制前置，命中后也不取消联网。
- 重试、反思、重规划和并发都需要明确触发条件、预算及终止条件。已有清晰结果时结束任务。

## 2. 透明度：展示计划、执行事实与依据

- 研究开始时向用户展示简明计划：目标、步骤、信息来源、步骤依赖和预期产物。
- 执行中展示当前步骤及其等待、执行、完成、受阻或失败状态，并说明工具选择和调用结果。
- 重规划时展示计划发生的变化及简要原因。审批、预算耗尽、缺少证据和工具不可用需要明确呈现。
- 报告中的关键结论可追溯到证据和来源；区分资料事实、分析判断和未解决的不确定性。
- 研究计划、审核状态、运行版本和预算在研究工作区与独立研究记录中展示；报告正文采用正常研究语言，保留发现、分析、图表、引用及简洁的方法说明。写作规范见[报告写作与研究记录](REPORT_WRITING_GUIDE.md)。
- 对外展示可理解的计划摘要与执行依据，日志和界面中的凭据、内部敏感数据按权限处理并脱敏。

## 3. ACI：工具接口也是产品接口

ACI（Agent-Computer Interface，代理与计算机交互接口）决定 Agent 能理解哪些操作、传递哪些参数，以及如何判断结果。工具说明、参数契约和错误反馈应共同维护。

每个工具的文档至少明确：

- **用途与选择条件**：适用任务、能力边界、只读或写入性质、使用前提。
- **输入**：参数含义、类型、默认值、范围、示例及应拒绝的输入。
- **输出**：结果结构、来源与证据字段，以及空结果和失败的区别。
- **运行边界**：权限与资料归属、出站限制、超时、预算、取消、重试及重复请求的处理方式。
- **错误与后续动作**：可恢复错误、需要用户处理的阻塞，以及允许的回退路径。

工具变更用当前需求的最小行为用例验证真实契约：有效调用的结果、输入拒绝、权限边界及相关失败状态。外部系统用替代实现时明确其契约和真实环境验证缺口。

**用户已明确禁止回归测试：未经另行明确要求具体检查，不新增、修改或执行回归测试，也不改名绕过。** “重视工具测试”不构成额外授权。仅文档变更采用实际内容与一致性审阅；不为文字修改编写代码测试。

## 框架与生产演进

LangGraph 等框架可以加快起步，选型应由当前需要的条件分支、并发、状态与恢复能力支撑。进入生产时，持续审查抽象层是否仍有价值；基础组件能更清楚地完成同一任务时，可以逐步减少包装和框架耦合。简化过程保留已需要的权限隔离、审批绑定、恢复状态和预算边界。

评审每项变更时，说明：它解决什么研究任务问题，结构是否足够简单，用户能否看懂计划与状态，工具契约是否清楚，以及实际验证了什么。具体操作边界见[研究执行边界说明](research-runtime-boundaries.md)，资料检索定位见 [README](../README.md)。

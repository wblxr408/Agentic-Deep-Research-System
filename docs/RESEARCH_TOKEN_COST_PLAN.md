## 1. 结论与证据

优先顺序是减少重复调用、缩小必要输入、扩大有效结果复用，再降低保留调用的供应商输入成本。保留现有 LangGraph、动态 DAG、Planner／Analyst／Reflection／Report 及工具；不把改成三个或一个 Agent 当作降本前提。

原根 `35225435-0693-49e5-853b-43de0aff43a9` 的最终记录为 6,092,491／6,100,000 Token、53／142 次工具调用，正文必核250／250、读者8标准、PDF图文66／66必核已完成。依据为 `outputs/quality-e2e-20261101-runtime/final-acceptance.json` 及 `docs/acceptance/research-quality-e2e-20261030.md`。这包含多次开发修复、合同调整和恢复，不能直接作为一次正常生产研究的成本基线，不能把全部消费归为冗余。

本轮源码审阅确认以下差量；没有通过付费重放测量节省量。

## 3. 第一优先：直接减少调用与输入

### 3.1 先定内容归属，再按章写作

复用当前写作计划，为必答问题、核心结论、决定性前提、具体课题及团队各指定负责章节和证据。前章已交付什么只传精简的归属／结论记录。每次写作输入包含当前问题与模式、所属内容单元、必要证据窗口、条件／反例、当前阶段Skill，以及真正被引用的跨章结论。

不再默认传 `preceding_chapters` 全文；涉及实际措辞衔接、矛盾或指代时再定向提供相关段落。全局整理处理衔接与结构，避免重新生成整稿。必要实验条件必须随数字保留；不能为缩小输入丢掉限定。摘要不是事实核验原文的替代物。

以每章等长L、共n章作说明，仅“此前章节全文”的重复输入就约为 `L×n×(n−1)/2`，尚不含原文。10章、每章3000 Token时是135000重复输入Token；这是示意计算，不是本项目测得的可节省量。

### 3.2 一个问题集，一次定向修复

Reflection负责材料／论证缺口，事实审核负责来源支持，读者审核负责问题覆盖和阅读功能，图文审核负责当前呈现与来源的对应。先列出各自独有覆盖，再去掉相同输入、判据和目的的重复调用；不预定整段删除Reflection。

审核统一返回问题、证据锚点、实质影响、最小修改范围和依赖。把同一稿上可合并的问题交给一次有界局部修复，减少“事实改一轮、阅读改一轮、图文再把同一内容改一轮”。有依赖的判断按顺序完成，不能为了合批让无效前提通过后续步骤。

写作能力拥有改稿，审核能力提供问题；审计稿不成为第二份正文。保留原稿、补丁和版本，修订只改目标单元。全局重写仅在结构或主论证确实失效时使用。

### 3.3 分级决定阻塞，而非降低事实标准

- 阻塞：核心结论、决定性数字／前提、错误归属、来源矛盾、缺失必答内容，以及会误导研究决策的图文。
- 定向修复：同一命题在同一阅读功能内的实质冗余、局部论证不足、引用定位问题；保留内容独有贡献。
- 提示：必要的摘要预告、就地条件重复、纯风格偏好及不影响结论的细节，不自动触发全稿返工。

次要事实一旦成为建议或核心结论的必要前提，就升级为必核。免核只能记为未核，不记为已支持。边界争议按原任务政策做一次有界影响复核；不同审核共享修订机会，不增加无限“审核是否太严”的元审计循环。

### 3.4 同源有界批次＋确定性格式处理

事实批次尽量按共享原文组织，只传一份重叠来源文字，每条主张仍绑定自己的可用范围。限制批次输入、主张数与输出容量；过大时拆分，避免截断、串证和重试。

结构输出使用实际端点支持的合同。已知无损字段移动、分组、去重和序列化由代码完成，保存原响应；真实语义缺失不能用投影伪装成功。同一操作的失败／修复次数在原根持续记录。高频输出以状态、锚点、影响和必要理由为主，避免反复输出整篇审计报告。

## 4. 第二优先：沿现有存储扩大有效复用

缓存读取顺序为已有持久化产物与收据→当前依赖有效性判断→仅为缺失或失效单元发起新调用。无需新建缓存管理器Agent、Redis服务或第二套RAG。

复用资格由可信代码比较已冻结的输入／依赖记录；不增加一个LLM来逐次决定是否命中。无法证明语义未变的编辑进入受影响审核，不用“看起来相似”作通过依据。同一主体、原根和完整操作绑定的并发重复请求沿现有数据库操作身份／租约合并：一个实际调用，其他消费者等待其收据和产物；实际消费只结算一次。已派发但结果未知时等待对账或按原恢复规则结束，不因等待超时再启动一份相同付费请求。

| 对象／现有落点 | 复用内容 | 失效条件与新增差量 |
|---|---|---|
| 原文／解析／原始页面：资料版本、`external_evidence.py`、`source_media.py` | 合法当前版本的全文、解析、页面 | 来源更新、权限变化、时效要求、no-store、解析合同变化；线索不是全文。查找可复用产物不强制模型重搜 |
| 分析：`research_context.py` | 问题与材料支持的分析单元 | 相关问题、前提、来源／反证或合同变化；逐步补单元依赖，不能仅凭文字未变放行 |
| 写作：`report_composition.py`与报告持久化 | 输入绑定的付费章节原始响应、合法分区 | 章节所属内容、必要材料、政策、模型变化；无关章节排版不应自动重写本章。旧合同产物仍保留为候选，不冒充新合同通过 |
| 事实：`claim_verification.py` | 有依据的判定，保留成功与失败原始记录 | 主张含义、指代／条件、来源版本／位置、权限、统计、模型及政策变化。正负结果都不能因恢复无条件重算或跨范围沿用 |
| 读者：`report_quality.py` | 当前有效维度及技术／行动材料包 | 覆盖、章节关系、主结论或相关内容变化；逐步实现受影响维度失效，不把整稿binding简单去掉 |
| 图文：`source_media_explanations.py`与呈现审核 | 原始页面、解释和有效来源支持 | 图页、引用段、图说、数据或当前呈现关系变化。纯分页可复用事实支持，但需核对新锚点、裁切和实际呈现 |
| 恢复：原执行控制／模型收据 | 已完成请求的完整输出及结算状态 | 未收到收据不等于未收费；未知派发不能当cache miss直接重发。不得清除旧消费和修订次数 |

判断复用需要“主张→必要上下文／前提→来源版本／范围→合同／模型／权限”的依赖记录。实现沿现有内容和审核记录存储关系，不引入GraphRAG服务。段落移动仍检查指代和章节角色；新来源即使支持旧结论，也可能增加反证，不能一概视作无影响。依赖不明时扩大到局部或全局审阅。

供应商缓存计量要尽早补齐；长有效期／新模型替代放在内容与应用复用之后。第一轮收益更可能来自章节输入、局部修订和避免重复审核，这是结合源码的优先级推断，具体数额待实际证据。

成本报告同时展示逻辑输入／输出、供应商缓存读写、已知费用与未知项、请求数、重复派发、审核有效复用／失效原因、必要问题覆盖、实质错误及阅读误拦。应用命中率按“本次确实可请求的有效操作”统计，供应商命中率按其原生分母定义，不能混为一个缓存率。

不设“609万直接降到某固定数”的验收；先固定同范围输入、模式、模型和质量合同，区分正常运行与开发修复。任何拟议降幅都只能作为预算目标，不能当实测效果。单次样本不报告P95；缺价格不报告确定美元节省。实际行为证据应来自用户另行明确授权的完整业务旅程；本轮未执行测试、回归、构建、探针或付费比较。

## 8. 百篇论文规模约束

已有机制接合：用户确认采用现有RAG管理目录，具体[复用／适配对照与顺序](CORPUS_RAG_INTEGRATION_PLAN.md)替代从零建设目录／解析／检索的设想。逐篇目录、来源与分级状态经现有资料／任务记录接合，RAG按需提供原文；当前top-k、原始任务账本和已索引状态不等于语料覆盖或已完成阅读。获取缓存、技术卡及补证沿原机制，仅补实际接口与失效差量，不把旧腾讯脚本或统计重跑为模型成本。

用户2026-11-01进一步提出：当前约5篇重点论文已经累计600万Token，若调研100篇怎么办。该消费说明当前端到端成本还没有规模化可用证据；即使其中含开发修复，也不能作为正常可接受单篇成本。不能直接承诺缓存能解决新100篇首读，也不能把历史根按20倍推算成确定预算。

### 8.1 研究范围与覆盖必须可见

区分“100篇覆盖＋问题驱动重点精读”和“100篇全部精读”。前者逐篇记录筛选／基础分析及哪些论文进入深读；后者100篇均须进入已约定的精读字段，不能以代表集或默认top-k替代。摘要阅读、全文基础提取、关键问题精读及缺全文分别记录，不将篇目清单当已读。论文版本／镜像按原身份依据处理，原件数不冒充独立成果数。

现有代码已有`reading_representatives`的逐篇／全部分支、代表选择和Analyst每2篇深读分包，并非只能输入5篇；这些局部机制不证明100篇已完成。规模合同需要从用户范围贯穿资料、分析、综合、内容／图计划、审核和导出。

### 8.2 每篇持久化、按主题综合、必要时回查原文

| 阶段 | 处理方式 | 减少重复的边界 |
|---|---|---|
| 语料与范围 | 建立所需100个成果的版本、来源、全文可用性、所需阅读层级、处理状态与缺口 | 去镜像但保留原件版本，不因上下文放不下静默丢掉后半部分 |
| 逐篇证据提取 | 沿现有技术卡保存问题、方法、机制、条件、基线、结果、局限、图注／原文位置；独立批次持久化 | 每个有效输入和字段合同只处理一次；摘要或模型卡不是已审核事实，支持状态仍分列 |
| 问题驱动深读 | 根据明确范围对全部或重点论文补必要字段与原文，长论文按结构补读 | 补缺字段／窗口，不每换章节就重读整篇；用户要求全部精读时不擅自降为20篇 |
| 主题证据矩阵 | 按共同研究问题、机制／方法、条件和反例归组，输出比较与证据引用 | 不为每篇生成一份完整报告，不默认进行100×99/2次两两模型比较 |
| 跨主题综合 | 消费主题结论、争议、条件及原文指针，关键冲突回查论文 | 聚合摘要用于导航，关键事实回到来源；不把多级摘要的幻觉累积为证据 |
| 报告与可视化 | 正文按问题论证，逐篇细节进入可追溯附录；图需求沿R8覆盖 | 章节只收所需主题、条件与证据；图块、表格和附录分页处理，不因篇数大省略所需产出 |
| 核验与修订 | 对实际输出中的必要主张、图事实与所需覆盖审核，按共享来源有界合批 | 不把100篇全部细节在每个章节重复审核；承诺全字段核验时如实计入额外成本 |

分组可沿已有技术分类、方法、问题及来源字段完成，不以新增GraphRAG、向量库或聚类Agent为前提。RAG按需提供原文窗口，不能以检索top-k命中代替100篇覆盖。模型输入仍需实际包含必要原文，给一个文档ID本身不等于模型已经读取。

### 8.3 批次与恢复必须承接总规模

逐篇／主题任务在原LangGraph／DAG与根准入内有界分批，完成即保存；受控并发只用于缩短时长，不记为Token节省。并发受实际模型限流、在途预留、时间和资源决定，不创建100个自治Agent或100份预算。单篇失败只重试该操作，未知派发先对账；恢复不得清空已完成99篇或重算所有章节。

核对每类限制的对象：代表选择、每批证据字节、单次输出、最多12个绘图项、最多8个原文页等不能混成“最多支持几篇论文”。保留每次资源边界，以持久化分页／分批承接总量；必需图超过单批时继续后续批次，不简单一次渲染100份PDF或直接解除全部限制。确有原根额度／期限不足时保留覆盖状态及缺口，不把100篇任务标成已完成。

### 8.4 先建立成本模型，再给具体额度

正常任务成本拆为：逐篇基础提取＋所需深读增量＋主题综合＋章节与图生成＋唯一必要主张审核＋受影响修订。开发修复、重复派发和恢复返工分别报告。预算按未完成论文／字段／主题／审核项计算，已完成项不再次整包预留。

以下仅是解释量级的算例，不是实测、保证或已批准的预算：若100篇各有12000个原生输入Token、逐篇提取输出1000Token，则一轮逐篇提取为130万Token；假设10次主题综合各16000输入＋2000输出为18万，10次章节生成各8000输入＋2000输出为10万，再假设核验、图文与必要补读40—90万，则总计约198—248万Token。若全部精读需要更多窗口、图像、更多字段或逐项核验，应增加相应项；不能把此算例用于证明所有100篇任务可在250万内完成。供应商缓存折扣影响费用，不改变该逻辑用量示例。

实际原文长度、所需精读字段、图数量、输出主张数、首次／复用状态和模型供应方确定后再报告额度与价格。本轮不调用真实模型或启动100篇研究来凑测量；今后按用户明确范围取得证据。首次新语料与已有99篇只新增1篇的任务分别计量，不能用热缓存结果冒充首次成本。

### 8.5 本轮实施与后续完成判据

不新建第二套百篇任务：1.1／1.2固定规模与范围，3.1记录论文／字段覆盖和主题内容归属，3.2补有界主题上下文，3.3／3.5保留论文到结论的依赖，5.2按剩余工作预测，5.5按篇／主题／审核观察成本；R8／12.9承接图文分批，6.2消费完整覆盖。新增篇目或新版本时只使对应论文、相关主题和依赖结论失效；主论证变化仍做必要全局复核。

“已有99篇再新增1篇”的增量例子指同一获准任务内的材料增长；跨任务复用继续沿现有显式资料范围、当前权限和合同，不能默认携带旧根审核批准，也不因此重派已完成Q0。热复用与首次处理的成本必须分别报告。

后续规模证据需包含：所需100篇各自去向与状态；明确“全部精读”时100篇的约定字段覆盖；失败隔离和接续；新增一篇或变更一篇后的实际受影响范围；同一任务所需图与导出完整；正常首次、复用及异常返工各自的真实用量。未经用户具体授权不执行100篇比较、测试、重放或付费旅程，不能用当前5篇结果宣称此目标已通过。

上述分层／外置产物选择参考[Anthropic上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。[Anthropic研究系统报告](https://www.anthropic.com/research/multi-agent-research-system)同时说明独立研究方向可并行、多Agent会增加Token开销；本项目借鉴任务边界与压缩交接，并不据此引入其Agent编队或照搬内部测量比例。

# 系统主动诊断与有限恢复 · 2026-10-26

用户要求暂停后系统自行查原因，不将查错工作交给用户。本轮沿用 `redesign-research-workspace` 的追加第8组，限于诊断、原权限与额度内的有限分析恢复及界面反馈。原完整研究质量优化仍暂停。

## 目标失败与实际发现

修改前，实际登录专用账号读取已停止任务，返回状态 paused，却没有 `pause_diagnosis`。前端未知原因退回“查看执行反馈了解原因”，用户需要自行查记录。

实现时实际观察到：短原文片段未达到当前问题的选取条件，也会返回 insufficient_context_budget；它不能被解释为总 Token 用尽。另一次连接失败后，按保守收据累计用量，原分析份额可能不足以再容纳原文和输出；恢复前必须检查下一次完整请求，而非只判断总额度还有 1024 Token。

## 实际操作

| 本次功能路径 | 结果 |
| --- | --- |
| 专用历史报告有两项核对问题 | 真实 GET 返回数量、对应主张和具体修订要求，Edge 不打开日志就能读到 |
| 用户主动暂停 | 诊断标为用户请求，自动恢复不可用，没有偷偷开始任务 |
| 专用账号继续已保存 Analyst 检查点 | 使用真实 API、图与数据库执行；模型端点固定为本机 `127.0.0.1:1`，真实连接失败，无外部推理调用 |
| 第一次分析连接失败 | 自动识别 SDK 的 APIConnectionError，真实图重新进入一次 Analyst |
| 再次连接失败 | 保存两次阶段尝试和一次根自动恢复；停止继续派发，诊断说明自动恢复仍失败 |
| 原任务边界 | 原总额度和创建时间保留，既有阶段两次上限有效，没有通过恢复新建根任务或重置用量 |
| Edge 反馈 | 直接显示“已尝试自动恢复1次”、失败结果和模型选择入口；真实 SSE 中能看到自动恢复事件，无未处理页面错误 |

最终自动恢复旅程选择了原份额足够的专用长篇预算，未在执行中增额。专用起始用量 37 是用于非零保留检查的准备数据；连接失败后的用量按原保守收据机制保留，不能将本机拒绝连接的记录称为实际外部 Token 账单。

早期准备文本短于现有片段选取阈值，未进入模型请求；随后一份原分析份额不足的样本在下一次拟合时停止。这些没有计为连接重试通过，分别促成诊断细分与恢复前完整请求份额判断。最终原份额充足的旅程观察到两次真实 APIConnectionError。

另对这两个实际保留案例通过本人真实 GET 核对诊断：缺少选入原文时给出资料补足入口；分析输入／输出超过阶段份额时给出调整研究额度／问题入口。后者修改前推荐“设置模型”，已修正为具体数额缺口，避免错误暗示更换大上下文模型能增加阶段份额。对照保存在 `context-baseline.json`、`context-results.json`。
